# 医养照护 SaaS 平台立项说明书

> 文档状态：草案，待项目发起人确认
> 版本：0.1
> 日期：2026-08-08
> 暂定代号：医养照护 SaaS（正式名称未定）

## 1. 立项背景

现有项目最初是面向单一门店的微信小程序原型，已经具备部分员工身份、服务记录、统计和云存储能力，但它不具备医养照护 SaaS 所需要的多机构隔离、合同证据链、老人电子档案、服务履约、原始影像保护、全面审计和监管接口能力，不能直接作为未来商业平台的核心系统。

首个真实业务场景位于甘肃兰州：机构工作人员协助老年客户领取或核销养老服务消费补贴，并将补贴转化为实际服务。日常业务同时涉及纸质及电子合同、上门服务、员工前中后打卡、照片和视频留证、合同及护理档案归档、核销材料整理等工作。

全国长期护理保险制度及监管要求正在发展，本项目需要提前形成一人一档、照护计划、服务记录、证据留存、费用结算、审计导出和标准接口能力，但在取得正式授权和完成对接前，不把“已经接入医保或长护险”作为产品事实。

## 2. 产品定位

本项目定位为：

> 面向养老、护理、社区服务及医养结合机构的多租户医养照护 SaaS，以一人一档、合同管理、照护履约、服务证据、补贴业务及未来长护险适配为核心能力。

产品属于 B2B SaaS：付费和签约对象是机构，工作人员是系统用户，老人及家属是机构服务对象，平台运营方负责软件及数据处理基础设施。

## 3. 立项目标

### 3.1 业务目标

1. 将老人建档、合同签署与归档、服务登记或派单、上门留证、签字确认、补贴核销材料整理形成完整闭环。
2. 让机构能够按老人、合同、员工、服务类型、时间、状态和资金来源快速检索资料。
3. 同时保留无水印原始影像和带系统水印的业务证据版本，并严格控制宣传用途。
4. 让兰州现有机构成为首个试点场景，验证基层工作人员能否持续使用，而不只验证界面能否演示。
5. 从第一天建立多租户和数据隔离能力，使同一套平台未来可以服务多家机构。
6. 为长护险、民政补贴及其他支付来源建立可配置的业务适配层，而不是把平台绑定在单一政策上。
7. 支持多人共同完成一次上门服务，团队材料可以共享，但每名参与者的身份、角色和参与确认必须独立留痕。

### 3.2 产品资产目标

项目成果应同时具备三种用途：

1. 条件成熟时，由发起人组建平台公司并商业化运营。
2. 创业条件暂不成熟时，作为完整、可验证的 B 端产品及工程作品。
3. 出现合适合作方时，以软件授权、白标交付、定制实施、联合开发或整体转让方式变现。

因此，交付物不能只有可点击原型，还应逐步形成源代码、需求文档、数据字典、部署说明、测试材料、知识产权记录和脱敏演示环境。

## 4. 主要参与方

| 参与方 | 定位 | 核心职责或诉求 |
|---|---|---|
| 平台运营方 | SaaS 提供者 | 产品研发、平台运营、安全、供应商及租户管理 |
| 机构管理员 | 租户负责人 | 机构配置、员工权限、合同及服务监督、材料导出 |
| 一线工作人员 | 移动端用户 | 建档、签约、上门服务、前中后打卡、影像及签字采集 |
| 护理/服务主管 | 业务审核人员 | 服务安排、可选派单、记录审核、异常处理、服务质量管理 |
| 老人及家属 | 服务对象/签署方 | 信息确认、合同签署、服务确认和宣传授权选择 |
| 财务或核销人员 | 资金业务人员 | 补贴台账、核销材料、结算和对账 |
| 平台运维人员 | 受限后台人员 | 系统健康维护；无业务必要时不得查看敏感明文数据 |
| 监管及接口方 | 外部主体 | 在正式授权范围内接收材料、数据或进行检查 |

## 5. 首个业务闭环

第一阶段以“兰州机构养老服务消费补贴履约”为落地闭环：

1. 建立老人电子档案并登记服务资格、联系人和必要护理信息。
2. 上传纸质合同扫描件，或发起合规电子签署流程。
3. 工作人员直接选择服务项目和一名或多名参与者，或由主管预先建立并派发服务任务；具体方式由机构配置。
4. 工作人员按机构规则完成服务前、服务中、服务后记录；多人协作时可以提交团队共享材料，也可以按项目要求分别提交个人材料。
5. 系统记录时间、位置、人员、设备及业务水印，保存原始影像和证据副本。
6. 老人或家属进行服务确认或签字。
7. 主管审核服务记录，异常记录退回补正。
8. 系统按要求整理合同、档案、服务记录、影像和签字，形成核销材料包与台账。

## 6. 核心产品原则

1. **多租户优先**：每条业务数据必须由服务端绑定租户，任何客户端参数都不能突破机构边界。
2. **原件优先**：合同原件、原始照片和原始视频采用私有存储、完整性校验和访问审计，不覆盖原件。
3. **证据与宣传分离**：履约留证不自动等于宣传授权；宣传素材必须存在单独、可撤回或到期的授权依据。
4. **最小必要处理**：老人身份、健康、护理和合同信息按敏感程度分级展示和授权。
5. **操作可追溯**：关键查看、导出、修改、审核、签章和删除操作必须留痕。
6. **外部接口可替换**：电子签、云存储、短信、地图和未来监管接口通过适配层接入，避免被单一供应商锁定。
7. **真实使用优先**：第一版评价标准是业务是否持续跑通，而不是功能数量。
8. **材料共享、责任独立**：多人协作可以共用日志和影像，但系统必须保留每名参与者及其确认记录，不能用一名员工的上传行为自动证明其他员工到场。

## 7. 非目标

以下内容不属于首次可用版本的立项目标：

1. 冒用或暗示国家医保、政府长护险官方平台身份。
2. 在未获授权前直接连接国家或地方医保生产接口。
3. 一次性建设覆盖全国所有政策差异的完整结算平台。
4. 面向老人个人开放完整 C 端商城或社交产品。
5. 远程飞检、AI 自动评估、复杂智能排班等后期能力。
6. 替代机构现有财务总账、工资、人事或完整 ERP 系统。
7. 未取得单独授权即将服务照片、视频用于宣传。

## 8. 分阶段路线

### 阶段 A：原型及业务验证

- 使用模拟或脱敏数据完成核心流程。
- 由兰州机构业务负责人及少量一线人员试用。
- 验证流程、字段、权限和操作负担。

### 阶段 B：单机构受控试点

- 完成必要的真实数据合规准备后，在首家机构小范围运行。
- 建立问题登记、培训、审核、备份和事件处理机制。
- 形成首个可验证案例及业务指标。

### 阶段 C：多机构商业试点

- 引入第二家及第三家机构，验证租户隔离和配置能力。
- 完成 SaaS 合同、数据处理协议、正式安全测试和运营支持体系。

### 阶段 D：监管及长护险适配

- 根据实际地区政策、机构资质和接口文档进行对接。
- 完成正式测试、验收和授权后，方可对外声明接口能力。

## 9. 立项成功判定

项目不以“代码写完”作为单一成功标准。首轮业务验证至少应证明：

1. 一个老人从建档、合同、服务登记或派单到服务确认和材料归档可以完整走通。
2. 一线人员在培训后能够独立完成主要操作。
3. 管理人员可以按多个条件找回合同和服务证据。
4. 原始影像、业务水印版本和宣传授权之间不存在混用。
5. 关键操作存在可审计记录。
6. 第二家机构接入时，无需复制一套独立代码。

具体数量和效率指标应在首轮试点前由业务负责人确认，不在本立项阶段虚构。

## 10. 当前主要风险与前置条件

1. 项目发起人尚未形成完整公司运营团队，试点必须依靠真实业务负责人和现场执行人员。
2. 平台公司注册地、品牌名称、云服务商、电子签供应商尚未最终确定。
3. 真实老人数据启用前，需要完成隐私文本、数据处理协议、权限设计和安全检查。
4. 电子签章不能采用简单印章图片代替，应由合规电子签服务或可靠电子签名机制完成。
5. 长护险及政府接口取决于地方实施、机构资质、平台评审、接口文档和正式授权。
6. 项目未来可能与发起人的任职单位产生知识产权或同业冲突，入职前版本及资产必须留有独立证据。

## 11. 本阶段决策请求

请项目发起人确认：

1. 是否认可上述产品定位和首个业务闭环。
2. 是否认可“先补贴履约、后长护险正式接口”的顺序。
3. 是否认可创业、求职作品和软件变现三种用途并存。
4. 是否同意第一版以真实持续使用为目标，而不追求一次完成全部平台能力。

确认后才能进入技术设计和开发任务拆解。
